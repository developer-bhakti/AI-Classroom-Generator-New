# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the Vite dev server
- `npm run build` — production build (outputs to `dist/`)
- `npm run preview` — serve the production build locally
- `npm run lint` — run Oxlint (config in `.oxlintrc.json`)

There is no test runner configured in this project.

Requires a `.env` file (see `.env.example`) with:
- `VITE_GEMINI_API_KEY` — from https://aistudio.google.com/apikey (optional `VITE_GEMINI_MODEL`, defaults to `gemini-flash-latest`; optional `VITE_GEMINI_IMAGE_MODEL`, defaults to `gemini-3.1-flash-image`). **Gemini image models are not on the free tier** — their free-tier quota is literally 0, so worksheet-image generation 429s until billing is enabled on the key's Google Cloud project. Text generation is unaffected.
- `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` — Supabase Project Settings → API
- `VITE_RAZORPAY_KEY_ID` — Razorpay API keys (the Key **Secret** must never go here; see `supabase/README.md`)

The dev server must be restarted after changing `.env`.

## Architecture

This is a client-only React + Vite app (React 19, react-router-dom v7, Tailwind v4) that generates classroom teaching resources (worksheets, lesson plans, quizzes, activity ideas, exam papers) via the Gemini API. There is no backend — auth, history, and saved content all live in `localStorage`.

### Generation pipeline

Every generator page (`WorksheetGenerator`, `LessonGenerator`, `QuizGenerator`, `ActivityIdeas`, `ExamPaper`) follows the same flow:

1. Page collects form data and calls `generateResource({ type, formData })` from `src/Services/aiService.js`.
2. `aiService.js` looks up a prompt builder from `src/Services/promptBuilder.js` (one per resource type: `buildWorksheetPrompt`, `buildLessonPrompt`, `buildQuizPrompt`, `buildActivityPrompt`, `buildExamPrompt`) and builds the prompt text from the form data.
3. The prompt is sent to `generateStructuredContent()` in `src/Services/geminiService.js`, which calls the Gemini `generateContent` REST endpoint directly (no SDK) with a fixed `responseSchema` forcing JSON output shaped as `{ title, summary, sections: [{ heading, items[] }] }`. Response shape is validated manually (`validateShape`) before use.
4. `aiService.js` attaches a type-specific note (estimated time/difficulty) and returns `{ title, summary, sections, note, prompt }` to the page.
5. The page renders the result and can call `recordHistory()` / `saveContent()` from `src/Services/contentStore.js` to persist it.

To add a new resource type: add a prompt builder in `promptBuilder.js`, register it in `PROMPT_BUILDERS` (and `NOTE_BUILDERS`) in `aiService.js`, add an entry to `RESOURCE_TYPES` in `contentStore.js`, and wire up a page + route.

**Exam papers keep the answers out of the paper.** `buildExamPrompt` asks Gemini for two separate lists and `generateExamContent` (`EXAM_SCHEMA`) returns `{ title, summary, sections, answerKey }`: `sections` is the student's paper (Section A / Section B, questions and options only) and `answerKey` is the teacher's key. `aiService` then runs `splitExamSections` (`src/Services/examPaper.js`) over `sections` as a safety net, moving any section headed like an answer key ("Answer Guide", "Marking Scheme", "Solutions", ...) into `answerKey` instead of showing it; the heading test is deliberately narrow so "Answer the following questions" stays on the paper. The key is stored in its own `generated_content.answer_key` column (not inside `sections`), so no screen that lists `sections` can show it, and `contentStore.fromRow` applies the same split to exam rows saved before the change (their old "Answer Guide" becomes the key). The key is only ever rendered by `TeacherAnswerKey`, a collapsed, labelled `<details>` on the Exam page and in the History and Saved previews. If `schema.sql` has not been re-run, `recordHistory` retries the insert without `answer_key` (the paper is saved, the key lasts only for the session) and logs a hint. There is no PDF export for generic exam papers; the Child Assessment PDF is already two parts (the child's paper with questions only, then the teacher's answers).

**Quiz rounds.** `QuizGenerator` plays the quiz itself, in rounds (`src/Services/quizRounds.js`, pure logic). Round 1 is the whole quiz; the results screen then shows the score ring, the level (same 90/75/60 bands as the child assessments, from the rounded percentage the student sees), a message written to the student ("You need to work on this part"), the wrong questions with the student's answer, the correct answer and a one-line "Why" (`explanation`, an optional field the quiz prompt asks Gemini for; older saved quizzes simply lack it), and a **Practise the N missed questions** button that starts round 2 with only those questions — repeating until none are wrong. `buildRound` reshuffles the options every round (quiz options were never shuffled in code before, so a model that puts the right answer first no longer gives it away). Round results are session-only, like the answers themselves.

**Image output.** `WorksheetGenerator` has a second, parallel path: `generateResourceImage({ type, formData })` in `aiService.js` builds a *layout* prompt (`buildWorksheetImagePrompt`) and calls `generateImage()` in `geminiService.js`, which hits a Gemini image model and returns a base64 `data:` URL. Both paths share `postToGemini()`, so image calls raise the same typed errors and route through `describeGeminiError()`. Image mode is the page's default; the "Text worksheet" toggle restores the structured-JSON path. Only image mode exists for worksheets — extend `IMAGE_PROMPT_BUILDERS` to add more. Images are **not** persisted: `generated_content` stores text columns only, and a base64 page would be megabytes per row, so image results are session-only and offered as a download instead of a Save.

**Class range.** The app serves **PG, Nursery, LKG, UKG, Class 1, 2 and 3 only**. `CLASS_SUBJECTS` in `src/Services/curriculum.js` is the single definition: `classOptions` and `subjectMap` are derived from it and imported by all five generator pages, the syllabus, the assessment and the dashboard — none keeps its own list any more. Records a teacher saved earlier for a higher class stay in the database but can't be chosen or created from the UI. Every generator prompt in `promptBuilder.js` opens with `audienceNote(className)` (who the learners are, how they read, and "simplify an advanced topic, never decline it"), so any topic comes back pitched at that age; the AI tutor likewise answers a child's off-topic question simply before returning to the lesson. To widen the range, add the class to `CLASS_SUBJECTS` and an `AGE_NOTES` entry (classes past Class 2 automatically get the text-led question mix; see `isYoungLearner`), and check the new subjects exist in `resourcePalette.js`.

**Resource colour scheme.** `src/Services/resourcePalette.js` is the single source of truth, used by **all five generator pages**. `getResourcePalette({ className, subject, type })` composes three dimensions into one shade:
- **subject** → the hue family (Math → royal blue, Biology → emerald, …). Every subject in `subjectMap` (`curriculum.js`) must stay mapped here; the older `Social Studies` / `Social Science` / `History` / `Physics` etc. entries are unreachable now but harmless, and are needed again if the class range is widened.
- **class** → the shade within it, walking a lightness/saturation ramp plus a small hue drift from PG (bright pastel) to Class 12 (deep). The app only serves PG–Class 3 (see **Class range**), so only the lighter end of the ramp is reachable today; the ramp is deliberately left at full length so widening the class list later needs no palette retune.
- **resource type** → a small hue offset (`TYPE_HUE_OFFSETS`, ±24° max) so a lesson plan and a quiz for the same class don't look identical.

All 880 type×class×subject combinations resolve to distinct hexes. Keep the type offsets small — larger values push a subject out of its recognisable hue family.

It returns three colours: `hex` (the shade), plus fixed-lightness `ink` (L24) and `glow` (L78) for text. Text must use `ink`/`glow` rather than mixing `hex` toward the foreground — `hex` ranges from very light to very dark across the ramp, so a mix-based text colour drops below contrast minimums at the light end (the amber/yellow subjects are the binding constraint). As tuned, the worst pair is 5.03:1 (light) and 5.77:1 (dark); re-run a full sweep after changing `LIGHTEST`/`DARKEST`/`ink`/`glow`.

Each page sets `--resource-accent` / `--resource-ink` / `--resource-glow` on its output card and adds `themed-output`; `.themed-output` in `index.css` uses them for the background tint, border, inset top bar, headings and note. Two gotchas: `.panel-card:hover` outranks `.themed-output`, so the inset bar is restated in `.themed-output:hover`; and `.exam-preview-card` sets its own `background`, so `.themed-output` only wins there because it is declared later in the file. Each page pins the palette at generation time (`outputPalette`) so editing the dropdowns afterwards can't re-tint output that's already on screen. `buildWorksheetImagePrompt` additionally feeds the colour name + hex + band tone into the image prompt.

Gemini error handling is centralized: `geminiService.js` throws typed errors (`GeminiConfigError`, `GeminiAuthError`, `GeminiRateLimitError`, `GeminiNetworkError`, `GeminiResponseError`), and `describeGeminiError()` converts them to a user-facing message. Generator pages catch errors from `generateResource` and render the result of `describeGeminiError(err)`.

**Model failover.** All *text/JSON* requests go through `requestGeminiJSON`, which tries `modelsToTry()`: the configured model (`VITE_GEMINI_MODEL`, default `gemini-flash-latest`), then `FALLBACK_MODELS` (`gemini-flash-lite-latest`). It moves on when a model times out, is offline, returns 5xx or 404 (retired model) or 429 — **not** for a rejected key, a blocked prompt or a malformed reply, which would fail the same everywhere. A model that fails over is tried last for 10 minutes (remembered in `sessionStorage`), so only the first request pays the wait (20s for quick requests, 40s for big jobs like a 20-question paper). This exists because the default alias has gone silent for hours at a time (every request timed out) while the lite model answered in about a second. Image generation is separate and does not fail over.

### Child assessment (`/syllabus`, `/assessment`, `/students`)

A separate pipeline from the five resource generators, built for preschool progress tracking: a teacher or parent checks "Is my child's knowledge as expected?" against the **syllabus for a chosen month**, the app marks an AI-written 20-question paper, finds areas of improvement and produces a printable **parent report**. A child is a roster row in `students` (no login of their own). All three routes need a subscription. The dashboard has the question (year / class / subject / month → `/assessment?year=&class=&subject=&month=`) and seven cards (Annual Syllabus, Monthly Syllabus, Student Details, Assessment, Results, Areas of Improvement, Progress Report) that deep-link into these pages (`?view=` picks the tab on `/syllabus` and `/students`).

**Syllabus** (`Syllabus.jsx`, `syllabusService.js`, table `syllabus_entries`): Annual → Term → Month, one row per academic year + class + subject + month holding a list of topics / learning outcomes. Terms are not stored: `TERMS` in `curriculum.js` maps months to Term 1–4 (Apr–Jun, Jul–Sep, Oct–Dec, Jan–Mar). A teacher's own row beats the shared one (`pickMonthEntry`); an **admin** can save a month as the shared **School syllabus** that every teacher sees (`is_shared`; one shared row per month via a partial unique index, so `saveSyllabusEntry` does select-then-insert/update instead of an upsert, and falls back to an update on a unique-violation race). "Suggest with AI" / "Draft empty months with AI" only ever fill the editor or an unsaved draft list. `supabase/seed-class2-math-syllabus.sql` is an optional seed that loads the Class 2 Maths textbook (NCERT *Joyful Mathematics*, 14 chapters split into 28 learning outcomes, one or two chapters a month from April in book order) as the shared School syllabus for academic years 2024-25 to 2028-29; it needs an admin to exist, and re-running never overwrites an edited month (`on conflict ... do nothing`). `AssessmentSetup` shows the editor inline when the chosen month has no syllabus, so nobody is blocked.

**Flow**, a stage machine in `Assessment.jsx` (`setup → evaluate → generating → taking → evaluating → results → report`, plus the optional `teaching → practice-*` stages):
1. `setup` — student, class, academic year, subject, month (or a whole **term** → an end-term paper). The syllabus loads automatically; the paper is built **only** from those topics.
2. `evaluate` — the teacher rates every topic Excellent / Good / Average / Needs Improvement (`RATINGS`). The ratings go into the paper prompt (extra questions on weak topics) and into the analysis.
3. `taking` — `QuestionPlayer`. Question mix depends on the class (`planQuestionMix`): PG–Class 2 get picture / multiple choice / fill-in (tap-to-choose) / match / simple-activity questions that an adult reads aloud; older classes get a text-led mix. `ASSESSMENT_LENGTH` = 20, `PRACTICE_LENGTH` = 10.
4. `results` / `report` — score, level, development areas, topic-wise bars, areas of improvement, then the parent report.

Code map: `assessmentService.js` orchestrates; `assessmentPrompts.js` holds the prompts; `assessmentGrading.js` is pure logic (no network); `assessmentReport.js` builds the parent report's content; `studentService.js` / `syllabusService.js` are the Supabase layers; `assessmentPdf.js` builds the teacher's paper + answers PDF; `curriculum.js` holds classes, subjects, the academic calendar and terms; `emoji.js` validates and draws pictures.

Things that are easy to get wrong:
- **Scoring is deterministic.** `checkAnswer()` marks against the answer key locally. The AI is used only for (a) a second opinion on *typed* answers that missed the key (it can never overturn a tapped answer), (b) diagnosis text, a home-activity plan and recommendations, and (c) a draft of the teacher's remarks. If the analysis call fails the teacher still gets the score and the topics to practise, with plain fallback text. Do not move marking into the model.
- **Levels come from the percentage, never from a stored label.** `getPerformanceLevel`: 90+ Excellent, 75+ Good, 60+ Average, else Needs Improvement. `studentService` re-derives `level` on every read and `LevelPill` takes a percentage, because the bands have changed before. `canonicalLevel()` maps the old names.
- **A topic needs practice** when its accuracy is under `MASTERY_THRESHOLD` (75%) **or** the teacher rated it Needs Improvement (`deriveWeakAreas`) — a child can guess a few right. Strengths are topics at/above the bar that the teacher did not flag.
- **Answer options are shuffled in code** (`shuffleChoices` in `normalizeQuestion`; pass `shuffleOptions: false` in tests). Models put the right answer first almost every time, which would let a child score by always tapping A. True/False and Activity keep their fixed order.
- **Questions map back to syllabus items by number.** The prompt numbers the items; each question returns `topicNumber`, and `normalizeQuestions` sets `topic` = `skill` = that item's exact text (falling back to wording similarity, then keeping the model's own label). That is what makes ratings, weak topics and `student_topics` mastery line up. Practice sets force every question's skill to the focus topic.
- **Pictures are emoji**, validated by `isEmojiString` (letters/digits are rejected so the answer can't be smuggled in as text) and only allowed in `picture`, picture options and match lefts. The PDF draws them as images from a canvas (`emojiToPngDataUrl`; null in Node, where they fall back to "[picture]"). Each question also carries one of the seven `SKILL_AREAS` (`summarizeAreas` recomputes area scores from saved questions + results, so no extra column).
- **Parent report = HTML, not jsPDF.** `ProgressReport` is a white "sheet" in every theme; `PrintPortal` renders a second copy outside `#root`, and the print stylesheet hides everything except `.print-root` (A4, one page for a typical report). The button is "Download / Print report" → the browser's print dialog ("Save as PDF"). The teacher's remarks box starts as the AI's draft and is saved in `assessments.teacher_remarks`.
- **Online teacher** (kept from an earlier brief): "Do you need an online teacher?" Yes → `TeacherSupport` writes a `teacher_requests` row that **admins** see and move through requested → assigned → completed on the Admin Dashboard (teachers can create/read, never change status — enforced by RLS); an optional "Practise with AI" chat tutor + 10-question retest lives there too. No → `ImprovementPlan` (activities and resources; prompts forbid inventing sites or book titles).
- **Child names are never sent to Gemini** — prompts carry only class, subject, syllabus topics and the child's answers.
- Assessments are English-only (`getLanguage()` is deliberately ignored): typed-answer matching and jsPDF's Latin-1 fonts (`pdfSafe` maps or drops anything else) don't support Indic scripts.
- `assessments.questions` holds the answer key and `results` the per-question outcome (incl. AI-accepted typed answers), so the PDF can be rebuilt without the AI. `requestPaper` drops malformed questions, retries up to 3 times (growing pause) on a bad response or a Gemini "high demand" 503, and throws if the paper is still short.
- Nothing is persisted mid-way: a row is written when a paper is submitted. `beforeunload` warns during `evaluate`, `taking`, `teaching` and `practice-taking`.

### Auth, data, and payments (Supabase)

Auth is real Supabase auth. `AuthProvider` (`src/context/AuthContext.jsx`, mounted in `main.jsx` above `BrowserRouter`) owns `session`/`profile`/`loading` and exposes them via the `useAuth` hook in `src/context/useAuth.js` — the hook lives in its own file so the provider file only exports a component (React Fast Refresh requirement). `ProtectedRoute` gates on `session`; `AdminRoute` additionally requires `profile.role === "admin"`.

Schema, RLS policies, and Edge Functions live in `supabase/` — see `supabase/README.md` for the one-time setup (run `schema.sql`, disable email confirmation, set env vars, deploy functions, promote an admin). Tables: `profiles`, `plans`, `subscriptions`, `payments`, `activity_log`, `generated_content`, plus the child-assessment tables `students`, `assessments`, `student_topics`, `teaching_sessions`, `teacher_requests` and `syllabus_entries` (owner-only RLS, except that a shared syllabus row is readable by everyone and writable only by admins; the write policies also require `student_id` to belong to the caller, so a guessed uuid can't attach rows to someone else's student).

**Access control:** the app is paywalled. `SubscriptionProvider` (`src/context/SubscriptionContext.jsx`) loads the user's subscription and exposes `isActive`, derived from `end_date > now()`. Routes passing `requireSubscription` to `ProtectedRoute` (`/worksheet`, `/lesson`, `/quiz`, `/activities`, `/exam`, `/saved`, `/history`) redirect to `/subscription` without one. `/dashboard`, `/subscription`, `/profile`, and `/settings` stay open. **Admins bypass the paywall entirely** — `isActive` returns true for them. `SubscriptionNag` re-opens a "buy a subscription" modal 10s after each dismissal; it is deliberately suppressed on `/subscription` itself, since otherwise it would cover the plan buttons and the Razorpay checkout window the user needs to reach.

Email confirmation and password-recovery links come back as `#access_token=...` in the URL. `supabaseClient.js` sets `detectSessionInUrl: true` so supabase-js consumes that hash into a session and strips it; turning it off makes a confirmed user land signed-out. `SignUp` passes `emailRedirectTo` derived from `window.location.origin`, but Supabase only honours origins listed under **Authentication → URL Configuration → Redirect URLs** — an unlisted origin silently falls back to Site URL (this is what sends production links to `localhost`). Branded email templates live in `supabase/email-templates/`.

`AuthContext` must not set `loading: false` until the profile (and therefore `role`) has resolved — `AdminRoute` reads `profile.role`, so flipping `loading` early makes a hard reload of `/admin` bounce an admin to `/dashboard`. Login routes admins to `/admin` and everyone else to `/dashboard`, reading the role directly from the DB rather than waiting on context.

**Password Management (`/password`, `Password.jsx`, `passwordRules.js`).** A dedicated page, reachable from the sidebar (right after Profile) and open to every signed-in user without a subscription. It is the only place the password form lives (Profile just links to it). Changing a password asks for the current one, verifies it with `signInWithPassword`, checks the new one with `validatePasswordChange` (6+ characters, different from the old, matching confirmation), then calls `supabase.auth.updateUser`; fields are cleared afterwards, nothing is stored, and only `password_changed` is logged (never the password). That current-password check is client-side defence in depth, not a security boundary; for server-side enforcement turn on **Authentication → Providers → Email → Secure password change** in Supabase. **Admins can never read a password** (Supabase stores only hashes, and this app deliberately keeps no readable copy: a stored plaintext password would be exposed by any database leak and reused by people on other sites). The Edit window's Password box is therefore for a *new* password and is left empty to keep the current one; beside it are Generate, Send reset link, and a one-line history from the activity log (`summarizePasswordActivity`: last changed and how). **Admin user management** (`Admin.jsx`): each row of the Users table has just **Edit** and **Delete** (Delete is disabled on your own row). Edit opens one window (`EditUserForm.jsx`): username (login email), name, password, account type, plan (with its price) and subscription end date, and sends only what changed through `applyUserEdits`, one part at a time so a failure (say, a taken email) does not lose the rest; a link at the bottom opens the older Manage window (pause, resume, cancel, delete the *subscription*, activity). Everything that changes another user's *account* needs the service-role key, so it goes through one Edge Function, `admin-manage-user` (`action` = `update` | `set_password` | `delete`; `setUserPassword`, `updateUserDetails`, `deleteUserAccount` in `adminService.js`). It verifies the caller's JWT, reads their role from `profiles` (the browser's claim is never trusted), refuses deleting yourself or demoting yourself, never leaves the app without an admin, keeps `auth.users.email` and `profiles.email` in step (restoring the login email if the profile save fails), and logs only field names (`user_edited`), `password_set_by_admin` or `user_deleted` (recorded against the admin, since the deleted user's own log cascades away) - never a password. Deleting relies on every user table being `on delete cascade`. The `prevent_role_self_escalation` trigger only restricts rows when `auth.uid()` is set, so the service-role function and the SQL editor can change a role or login email while a signed-in browser user cannot. Until the function is deployed the window says so; plan and end-date changes use the subscription table directly and still work. A reset link signs the person in with a recovery session: `supabaseClient.js` notes `arrivedViaRecoveryLink` before supabase-js strips the `#...type=recovery` hash, `AuthContext` exposes `passwordRecovery` / `endPasswordRecovery` (also set by the `PASSWORD_RECOVERY` event and remembered in `sessionStorage` so a reload does not demand the old password they have forgotten), `RecoveryRedirect` in `App.jsx` sends such a session to `/password`, and the page then skips the current-password field. The link's `redirectTo` is `<origin>/password`, which must match the **Redirect URLs** allowlist (`<origin>/**`). The Login page's "Forgot Password?" link is still a dead `href="#"`.

Security invariants worth preserving:
- `payments` has **no client write policy** at all; it is written only by the Edge Functions using the service-role key. `subscriptions` is the same for regular users, but admins may write via the `subscriptions_admin_manage` policy — that check runs `is_admin()` inside Postgres, so it can't be spoofed from the client. Admin mutations live in `src/Services/adminService.js`.
- Subscription status is `active | paused | expired | cancelled`. Pausing stores `paused_at`; resuming adds the paused duration onto `end_date` so a pause never costs the user days. Use `describeSubscriptionStatus()`/`statusPillClass()` from `subscriptionService.js` rather than reading `status` directly, since "expired" is derived from `end_date`.
- `profiles` has a `prevent_role_self_escalation` trigger because RLS grants row access, not column access — without it a user could PATCH their own row to `role='admin'`.
- Policies that check admin-ness call the `SECURITY DEFINER` `is_admin()` function; querying `profiles` directly inside a `profiles` policy would recurse.
- The Razorpay key **secret** exists only as a Supabase Edge Function secret. Anything `VITE_`-prefixed ships in the browser bundle.
- `subscriptions.status` is never swept by a cron job, so active-ness is derived from `end_date > now()` via `isSubscriptionActive()` (`src/Services/subscriptionService.js`), not read from the column.

`contentStore.js` is a Supabase-backed external store following the same `subscribe`/`getSnapshot` pattern as `sidebarStore.js`, consumed via `useSyncExternalStore`. It caches rows in memory so `Navbar`'s search stays synchronous; `AuthContext` calls `initContentStore(userId)` on sign-in and `resetContentStore()` on sign-out (skipping the reset would leak one user's cache to the next on the same tab). Mutations (`recordHistory`, `saveContent`, `removeSavedContent`, `removeHistoryEntry`, `clearHistory`) are now **async** and update the cache optimistically. History and Saved are one row with an `is_saved` flag, so deleting from History is a hard delete that also removes it from Saved. `recordHistory` is the single choke point where `resource_generated` activity is logged, so the five generator pages don't each need to.

Theme and generation language remain in `localStorage` — they're device preferences, not account data. Theme (`light`/`dark`) is stored under `adiuvaret-theme` and applied via `data-theme` on `document.documentElement`; `App.jsx`, `Login.jsx`, `SignUp.jsx`, `Navbar.jsx`, and `Settings.jsx` each read/write it independently. Language (`adiuvaret-language`) is read by `aiService.js` to translate generated output.

### Routing and layout

All routes are defined in `src/App.jsx`. Every authenticated page wraps its content in `<ProtectedRoute>` (or `<AdminRoute>` for `/admin`) and renders the shared `Sidebar` + `Navbar` shell (see `WorksheetGenerator.jsx` for the canonical layout: `.app-shell` > `Sidebar` + `.main-panel` containing `Navbar` and a `.content-area`).

**Scrolling.** `.app-shell` is exactly one screen tall (`100dvh`) with `overflow: hidden`, so the window itself never scrolls: `.main-panel` (top bar and content) scrolls on its own and the sidebar stays put. The sidebar only scrolls inside itself when the menu is taller than the window (so Logout stays reachable), and `Sidebar` scrolls the current page's item into view because every page re-mounts its own sidebar. `.main-panel` has `overflow-x: hidden`, so a child wider than the window is clipped instead of causing sideways scrolling; wide tables need their own `overflow-x: auto` wrapper. Because the window no longer scrolls, use the `.main-panel` element (not `window`) for any programmatic scrolling; `scrollIntoView` already works. `.eval-footer` is `position: sticky`, which now sticks to the bottom of `.main-panel`.

Note: `src/Pages/ExamPaperGenerator.jsx` exists but is not imported anywhere — `ExamPaper.jsx` is the page actually routed at `/exam`. Confirm which one is intended before editing exam-paper behavior.
